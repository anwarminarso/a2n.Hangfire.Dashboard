# Changelog

## Unreleased

> Behind cookie-based authorization, every dashboard page load made the server open SignalR client connections to its own public URL. Those connections carry no user cookie, so they always got HTTP 401. The first response waited for them, and every tab then fell back to polling storage on its own ([#61](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/61)). The dashboard's components now receive broadcasts in-process. The ad-hoc demand rollup can be turned off, and the README documents which reads use the adapter's connection string. With a slow or unreachable storage, open tabs, health probes and the background loops could also block more and more thread-pool threads until the host stopped responding ([#64](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/64)). The dashboard now limits how many storage calls it runs at once, its refresh loops never overlap and back off while storage is failing, and the health checks skip what storage can't answer. `IsReadOnly` now hides and refuses every action that changes jobs, recurring jobs or queues ([#73](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/73)). On .NET 10, a host without Blazor components of its own (a Web API or SPA host) had no `blazor.web.js`, so the dashboard never went interactive; the net10.0 build now serves its own copy when the host has none. Adds `DashboardUIOptions.EnablePrerendering`, `HeatmapOptions.DemandRollupEnabled`, `DashboardUIOptions.Polling` (`PollingOptions`) and the public `DashboardMetricsFeed`, `DashboardStorageGate` and `DashboardCircuitState`; `MetricsBroadcastService` and `AnalyticsBroadcastService` take the feed and `DashboardUIOptions` as new constructor parameters; no public API removals; no migration.

### Fixed

- **The dashboard goes interactive on .NET 10 hosts without Blazor components of their own.** On .NET 10, `_framework/blazor.web.js` is no longer embedded in the framework. It comes from the `Microsoft.AspNetCore.App.Internal.Assets` package, which the SDK restores only for a host that has a `.razor` file or sets `RequiresAspNetWebAssets`. The package's `build`/`buildTransitive` props set that property, but NuGet doesn't import package props during restore, so it never took effect. A Web API or SPA host installed from NuGet therefore served no script: the dashboard rendered, but nothing responded to clicks. 2.5.7 behaves the same; .NET 8 and .NET 9 hosts were never affected. The README claimed NuGet consumers didn't need the property.
  - **The net10.0 build carries a copy of the script**, taken from ASP.NET Core 10.0.12, and serves it at `{path}/_framework/blazor.web.js` only when the host doesn't serve its own. The host's copy, which matches its runtime, still wins; a host gets it by setting `RequiresAspNetWebAssets` in its own `.csproj`. The net8.0 and net9.0 builds don't include the copy.
  - **Startup says where the script comes from.** When the host has no script, the dashboard logs once: at Information when it serves its bundled copy, and at Warning on .NET 8 and .NET 9, where nothing can serve it (typically a build output run outside `Development`).
- **Search on the generic provider finds jobs whose type the dashboard can't load ([#70](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/70)).** On Redis, InMemory and every storage without a bundled adapter, every search scan skipped a job whose `Job` was null. That is the case for any job whose type the dashboard process can't load (Hangfire.SqlServer's monitoring API, for one, returns the DTO with `Job = null` and the invocation data set), so a dashboard deployed without the job assemblies found nothing, for any query or filter. A Failed page group could also list jobs that its **Search all jobs with this exception** link didn't find.
  - Such a job is now kept when its invocation data is there. Its row is named `Type.Method` from the invocation data and takes the queue from it; the name filter matches the class and method names in it, and the arguments filter its arguments, as for a loaded job. The Exception filter only needs the job id, so it finds them as it is. A job with neither is still skipped.
  - Search by job id, the tag search and the slowest-jobs list also name such a job from its invocation data instead of `Unknown`.
  - Class names read from invocation data now drop generic arguments and the outer class of a nested type, as `Type.Name` does (``Repo`1``, `Inner`), on the job lists as well.
- **Generic-provider search no longer lists a job twice when it changed state while still in its queue ([#68](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/68)).** A job leaves its queue only when a worker fetches it, so a job deleted or succeeded while enqueued is still in the queue. The generic provider (Redis, InMemory and other storages without a bundled adapter) listed every queue entry as Enqueued, so such a job was found twice: once as Enqueued and once in its actual state. Queue entries no longer in Enqueued state are now skipped; the scan of the job's actual state finds it. The SQL Server and PostgreSQL adapters read the current state from the `Job` table and weren't affected.
- **Pages no longer wait for failed hub connections, and tabs no longer poll storage independently ([#61](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/61)).** The sidebar, the Dashboard page and Analytics Overview built a `HubConnection` to `{AppPath}/hubs/dashboard` from inside the server process. `DashboardUIOptions.Authorization` applies to `/hubs/*`, so any filter that checks `HttpContext.User` rejected it. Behind a TLS-terminating proxy the prerender pass also used an `http://` base URL, which added a redirect that turned the negotiate POST into a GET. The failure was swallowed, so each circuit started its own 3-second `GetStatistics()` timer (plus `GetServers()` on the Dashboard page) and `MetricsBroadcastService` never had a subscriber. Even when the connection succeeded (for example with `LocalRequestsOnlyAuthorizationFilter`), it was an unnecessary round trip that required the server to reach its own public URL.
  - **Components subscribe to `DashboardMetricsFeed`, a singleton in the same process.** No network hop and no credentials are involved. In-process subscriptions count towards the same subscriber gate as hub clients, so the broadcast services still only query storage while someone is watching. `DashboardHub` and its `MetricsUpdated` / `AnalyticsUpdate` messages are unchanged for external clients.
  - **One storage read per interval, whatever the number of tabs.** The metrics broadcast now carries the server list along with the statistics, and the Dashboard page renders the payload instead of calling `GetStatistics()` and `GetServers()` again on every broadcast. Opening a page reuses the latest snapshot while it is fresh, so the prerender, the interactive render and other tabs opening at the same time share one read.
  - **Subscriptions and timers start only once the circuit is interactive** (`OnAfterRender`), so the prerender pass no longer sets up connections or timers.
- **`StatsPollingInterval` is honored.** The option was declared but unused, and the metrics broadcast was hardcoded to 2 seconds. It now sets the broadcast cadence (milliseconds, at least 500, default 2000). The broadcast also keeps a fixed cadence, like the analytics broadcast, and backs off while storage is failing ([#64](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/64), below).
- **A slow storage no longer starves the host's thread pool ([#64](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/64)).** Hangfire's storage APIs are synchronous, so every dashboard read holds a thread until storage answers, including the wait for a pooled connection. The pages refreshed on `System.Threading.Timer` callbacks, which fire every period whether or not the previous one has returned. With storage slow, each open tab kept adding blocked threads, and the reads queued for the same connections the Hangfire server needs for its heartbeat. The health probe waited on its read with `Task.Wait` and left it running after a timeout, so every probe after a timeout blocked one more thread. The background broadcasts and rollups ran on `PeriodicTimer`, which starts the next read at once when one takes longer than the interval.
  - **At most `Polling.MaxConcurrentStorageCalls` (default 8) of the dashboard's storage reads run at once**, across every tab: the realtime counters, the health checks, the Dashboard page's history chart, and the loading and refreshing of Processing, Job Details, Queues, the job lists, Retries, Recurring Jobs, the Throttling semaphore page, the sidebar's tag count and the live job console. Further reads wait without holding a thread. A read keeps its slot until storage actually answers, even after the page has stopped waiting, so the dashboard never blocks more threads than the limit. Search, admin actions (requeue, delete, trigger), the Analytics queries and the background rollups don't go through it.
  - **Refresh loops never overlap and back off.** Each page, the health card and the live console now schedule their next refresh once the previous one has finished. A refresh that fails, or takes at least `Polling.SlowCallThreshold` (default 5 s), doubles the delay before the next one, up to `Polling.MaxBackoffInterval` (default 60 s); the first one that succeeds in time restores the normal interval. While the browser is disconnected the loops pause, and they refresh as soon as it reconnects.
  - **The background loops keep a fixed cadence and back off the same way.** The metrics and analytics broadcasts, `DemandRollupService` and the rollup collector of `a2n.Hangfire.Dashboard.Rollup` count their interval from the start of one read to the start of the next. A read that fails or takes the whole interval delays the next one instead of starting it straight away.
  - **The health checks are asynchronous and bounded.** The `storage` probe reuses the realtime counters' latest read when it is younger than `StatsPollingInterval`, and reports how long that read took. The feed starts no second read while one is still blocked, so a stalled storage costs at most one thread however often `/healthz` is probed. The other checks read through the storage call limit, each under `HealthThresholds.StorageProbeTimeoutMs`. `HealthReportCache`, used by the endpoints, the `IHealthCheck` adapter and the hero card, awaits the checks instead of running them on a pool thread.
  - **The sidebar's tag count is shared** across tabs (15-second cache), and Processing and Queues take the server list from the realtime counters' snapshot instead of reading it again.

- **`IsReadOnly` now blocks every action that changes jobs, recurring jobs or queues ([#73](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/73)).** It was documented as hiding the action buttons, but only the Job Builder, the Failed page's group actions, the Queues page, the maintenance banner and the heatmap's schedule edit honored it. A host that set it to give people a view-only dashboard still let them requeue, delete, enqueue and trigger jobs.
  - **The services refuse them.** `HangfireMonitorService.RequeueJob`, `DeleteJob`, every `RequeueJobs` / `DeleteJobs` overload, `RequeueJobsInBatchesAsync` / `DeleteJobsInBatchesAsync` (before any batch runs), `TriggerRecurringJob(s)`, `RemoveRecurringJob(s)`, `StopRecurringJob` and `StartRecurringJob` throw `InvalidOperationException` in read-only mode, and so do `QueueOperationsService.PauseQueue`, `ResumeQueue`, `EnableMaintenanceMode` and `DisableMaintenanceMode`. `EnqueueJob` and `CreateOrUpdateRecurringJob` keep returning a failed `JobOperationResult`, as before. Hiding a button alone wouldn't be enough, since a Blazor event handler can still be invoked.
  - **The pages hide them.** In read-only mode the job lists (Enqueued, Fetched, Processing, Scheduled, Succeeded, Failed, Deleted, Awaiting) and Retries show no Requeue, Enqueue or Delete buttons and no selection checkboxes. Job Details has no Requeue or Delete, and Recurring Jobs has no Trigger, Delete, Create, Edit, Stop or Start. The Enqueued page no longer links to the Enqueue page.
- **Generic-provider search reads failed jobs through `IFailedJobPageSource` ([#69](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/69)).** When a storage adapter registers a page source, the generic provider used it for the Failed page's grouping but not for searching Failed jobs, which still called `IMonitoringApi.FailedJobs`, the path the page source replaces. Search now reads through the page source too. None of the bundled adapters was affected: PostgreSQL has its own query provider and SQL Server registers no page source.
- **Confirmation dialogs work from the keyboard and with screen readers ([#74](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/74)).** `ConfirmModal`, which confirms the dashboard's deletes and **Requeue all** / **Delete all** on the Failed page, renders Bootstrap's modal markup without Bootstrap's JavaScript, so none of a modal's keyboard handling was there: focus stayed behind the backdrop, Tab moved through the page underneath, and Escape did nothing.
  - **Focus moves to Cancel when the dialog opens**, the safe choice for a destructive action, and goes back to the button that opened it when the dialog closes. Tab and Shift+Tab cycle through the dialog's buttons. This is a small helper in `nav.js` (`hfModal`).
  - **Escape cancels**, like the Cancel button.
  - **The dialog is announced as one.** It has `aria-modal="true"`, is named by its title (`aria-labelledby`) and described by its message (`aria-describedby`), so a screen reader reads the question along with the focused Cancel button, and the close button is labeled "Close".

### Changed

- **Health checks skip what storage can't answer ([#64](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/64)).** When the storage probe fails or times out, the other checks are no longer run, since each could only fail after its own timeout. `/healthz/ready` and `/healthz/full` report each of them `Unhealthy`, with the description `Skipped: the storage probe failed.` and `"skipped": true` in `data`; the overall status is `Unhealthy` as before. A check other than `storage` that times out is reported `Degraded` with `"timedOut": true`. The hero card lists only the storage issue in that case.
- **Back-off is logged once per change of state ([#64](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/64)).** A refresh loop logs a Warning when it starts backing off and an Information message when it recovers, instead of an entry on every tick. This replaces the analytics broadcast's per-tick "Analytics broadcast took …" warning and its per-tick Error on failure, and the per-tick "poll failed" Error of both rollups. The rollup collector logs a failed pass at Error, once, when it starts backing off. Read errors the rollups catch inside a pass are still logged on each pass.
- **Page refresh intervals are measured from the end of one refresh** to the start of the next, rather than from the start of each ([#64](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/64)). With a fast storage the difference is the duration of the read.
- **The SQL Server test suite no longer skips itself when its target frameworks run at the same time ([#72](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/72)).** `dotnet test` runs it for net8.0, net9.0 and net10.0 in parallel against one server, and each run installed Hangfire's tables into its own schema through `UseSqlServerStorage(PrepareSchemaIfNecessary = true)`. Concurrent installs into one database deadlock on SQL Server (error 1205); Hangfire retries three times and then only logs a warning, so the run seeded a schema with no tables, and `SqlServerFixture` turned that error into a skip of every test. A local run looked green while one or two frameworks never ran. The fixture now installs the tables itself under an application lock (`sp_getapplock`) that every run of the suite takes, and only skips when the server can't be reached. Once connected, a failure to prepare the schema fails the tests instead of skipping them.
- **The PostgreSQL test suite skips only when the server can't be reached ([#85](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/85)).** `PostgreSqlFixture` wrapped creating the schema, installing Hangfire's tables and seeding in a catch-all, so any failure after connecting, such as a permission error or a failed seed, turned into a skip of every test, and the half-prepared schema was left behind. As in `SqlServerFixture` ([#72](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/72)), only a failure to open the connection skips the suite now, with the reason in each skip message. A failure after that fails every test, and the schema is dropped whenever the server was reachable.

### Added

- **`DashboardUIOptions.Polling` (`PollingOptions`) ([#64](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/64)).** `MaxConcurrentStorageCalls` (8), `SlowCallThreshold` (5 s) and `MaxBackoffInterval` (60 s) as above, and the intervals that were hardcoded: `FastPageRefreshInterval` (3 s: Processing, Job Details, Queues), `PageRefreshInterval` (5 s: the job lists, Retries, the maintenance banner), `SlowPageRefreshInterval` (10 s: Recurring Jobs, the sidebar counts), `ConsoleRefreshInterval` (2 s), `HealthCardRefreshInterval` (10 s), `HealthReportCacheTtl` (5 s), `AnalyticsBroadcastInterval` (5 s) and `RollupPollInterval` (60 s). The defaults are the previous values. `TimeSpan.Zero` turns a refresh off: the page still loads when opened, the health card keeps its Refresh button, `AnalyticsBroadcastInterval` stops the live Analytics updates and `RollupPollInterval` stops both rollups. The README's [Polling and Slow Storage](README.md#polling-and-slow-storage) section describes them.
  - **API.** `DashboardStorageGate` (singleton) runs synchronous storage calls under the limit; `DashboardCircuitState` (scoped `CircuitHandler`) tells whether the circuit is connected. `HealthCheckService` gains `CheckLivenessAsync`, `CheckReadinessAsync` and `CheckFullAsync` and a constructor that takes the metrics feed and the gate; the synchronous methods and the previous constructor are kept and block the calling thread. `HealthReportCache` gains a constructor that takes `DashboardUIOptions` for its default `Ttl`; the previous one is kept. `DashboardMetricsSnapshot.ReadDuration` says how long the snapshot's read took. `HealthHeroCard.RefreshIntervalMs` is now `int?` and defaults to `HealthCardRefreshInterval`.
- **`DashboardUIOptions.EnablePrerendering`** (default `true`). Set it to `false` to skip the server prerender pass: the first response is a lightweight shell and each page initializes once, when the circuit connects, instead of twice.
- **`HeatmapOptions.DemandRollupEnabled`** (default `true`) turns off the ad-hoc demand rollup ([#61](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/61)). With the SQL Server and PostgreSQL adapters, `DemandRollupService` polls recent executions every 60 seconds through the host's Hangfire storage, whether or not anyone has the dashboard open, and it couldn't be turned off. With the option set to false the poll doesn't start: the heatmap's Ad-hoc and Combined layers get no new demand, and weeks already collected stay readable until they fall out of the lookback. The poll also no longer runs when the heatmap itself is disabled (`Heatmap.Enabled = false`), since nothing reads its data then. Rollup-metrics adapters are unaffected, because their collector also feeds Analytics.
- **The Failed page groups failed jobs by exception ([#53](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/53)).** An Exception filter next to the page-size selector lists the kinds of failure, most failed jobs first. Each entry shows the short exception type (`DbUpdateException → SqlException` when one wraps another, full names in the tooltip), the normalized message, the top frame and the number of jobs. Selecting one shows that exception's total and the jobs that failed most recently; the page-size selector sets how many. "All exceptions" is the default and shows the page as before, without running any grouping query. The groups load the first time the filter is opened, or when the page is opened on one (`jobs/failed?exception=v1:…`, so a group can be linked), and refresh when the failed count changes while a group is shown or the list is open; otherwise they are read again the next time the filter is opened. They run under `DashboardUIOptions.SearchTimeoutSeconds`; a timeout or an error is reported under the list, and the list of failed jobs keeps working. The filter is a select-only combobox that works from the keyboard: arrow keys, Home and End move through it, Enter or Space selects, Escape closes, and focus stays on the filter.
  - **Stored fingerprints are counted exactly.** The SQL Server and PostgreSQL adapters group the `FailureFingerprint` parameter of Failed jobs in one query. It looks the parameter up for each failed job through the `Job` state-name index and the `JobParameter` index, and never reads `State`. Looking the parameter up per job, instead of joining the two tables, keeps the cost in line with the number of failed jobs. As a join, both databases chose to scan the whole parameter table, which holds every job's parameters. A value counts only when it is a current-version fingerprint, matched in SQL exactly as `FailureFingerprint.IsCurrentVersion` does (case-sensitive, no trailing characters). Anything else is recomputed.
  - **Failures without one are fingerprinted on the fly.** These are failures recorded before `UseDashboardFailureFingerprintFilter()` was registered, or on a server without it. They are fingerprinted from their state data and their stored job type, read from the invocation data rather than `GetJobData`, so the result is the same on every adapter. At most `JobFilterCriteria.CountLimit` (1,000) of them are read, the most recent failures first. Beyond that the page says the counts are lower bounds (`1,000+`) and, on the SQL Server and PostgreSQL adapters, that registering the filter gives exact counts. Nothing is written back, so this works in read-only mode.
  - **Labels come from one sample job per group**, the one that failed last, for the 50 largest groups only. The adapters load all the samples in one query.
  - **A group's jobs come most recently failed first, on every storage ([#71](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/71)).** A job that was scheduled, retried or requeued before it failed is placed by when it failed, not when it was created, so the group view's Failed column runs in order and the label's time is the group's latest failure. The SQL Server and PostgreSQL adapters order by the id of the job's current state, which grows with every state change and is read from the `Job` table, so the ids behind Requeue all and Delete all still never read `State`. The generic provider orders by `FailedAt`, as it did. On SQL Server, the grouping queries that do read a job's state seek it by `State`'s key, `JobId` and `Id`, instead of reading the whole table.
  - **Other storages.** The generic provider (Redis and others) fingerprints the latest 1,000 failed jobs in memory with the same function, with or without the filter (`FailureGroupsResult.UsesStoredFingerprints` is false there, so the page doesn't suggest the filter). It keeps jobs whose type the dashboard can't load, as the provider's search now does too ([#70](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/70)).
  - **New provider API.** `IStorageQueryProvider` gains `SupportsFailureGrouping`, `GetFailureGroupsAsync` and `GetFailureGroupJobsAsync`, all default interface members that report grouping as unsupported. Third-party providers keep compiling, and the filter stays hidden for them. `JobSummaryDto` gains `Reason` and `InvocationData`, so group rows look like the other job rows.
  - Analytics → Failures, the retry summary on Job Details and the Exception filter now share one way of shortening exception type names.
- **Requeue all and Delete all for an exception group ([#53](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/53)).** With a group selected on the Failed page, two buttons next to Requeue and Delete act on every failed job with that exception, not only the ones shown. They are hidden when `DashboardUIOptions.IsReadOnly` is set.
  - **Only a snapshot is touched.** The click reads the ids of the group's jobs first, and the confirmation (for both actions) shows their exact number and the group's label. Jobs that fail into the group afterwards are left alone. The ids are every failed job with the stored fingerprint plus the fallback members the grouping found, so when the counts are lower bounds, older failures that weren't read are not included; the confirmation says so.
  - **Only jobs still in Failed are changed.** Every state change passes `expectedState: "Failed"`, so a job that was retried, requeued or deleted in the meantime is skipped. The summary at the end says how many were changed and how many were skipped, then the groups and the list are read again.
  - **500 jobs per batch.** Each batch is one `jobs.requeued` or `jobs.deleted` audit entry, with the `requested` and `succeeded` counts and the group's `fingerprint`. Progress is shown as "Requeued 1,500 of 12,345"; Cancel, or leaving the page, stops after the batch in progress. If a state change fails partway through a batch, the run stops there, the batch's audit entry still records the jobs it changed (with an `error` key), and the page says exactly how many jobs were changed.
  - **Row selection is back in the group view**, with Requeue and Delete for the selected rows. On the Failed page, those buttons (in the group view and on the full list) now also change only jobs that are still failed, where they used to requeue or delete a selected job whatever state it had moved to.
  - **API.** `IStorageQueryProvider.GetFailureGroupJobIdsAsync` returns the ids of a group's jobs that are still failed, most recently failed first. The SQL Server and PostgreSQL adapters read them from the `Job` and `JobParameter` indexes, never `State`; the default implementation takes them from `GetFailureGroupJobsAsync`. `HangfireMonitorService.RequeueJobs` and `DeleteJobs` gain overloads that take a `fromState` (passed to Hangfire as the expected state) and extra audit metadata. The one-parameter overloads are kept as they were, so assemblies compiled against 2.5.x keep working without a rebuild. All of them now write the batch's audit entry even when a state change throws, with the jobs changed before it, and then rethrow. `RequeueJobsInBatchesAsync` and `DeleteJobsInBatchesAsync` run them in batches of `BulkActionBatchSize` with progress and cancellation and return a `BulkJobActionResult`; a failed batch doesn't throw but ends the run with `BulkJobActionResult.Error` set and counts that include the jobs it changed. `ConfirmModal` takes an optional `ConfirmIcon` and `ConfirmClass`.
- **Search filters jobs by exception ([#53](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/53)).** An Exception filter in Advanced Filters on the Search page finds every job that failed with one kind of failure, in any state: still failed, requeued and succeeded since, or deleted, since the `FailureFingerprint` parameter survives both. It combines with every other filter and keeps the 1,000-match count and newest-first paging from [#45](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/45).
  - **Exact match on the stored value.** The SQL Server and PostgreSQL adapters add an `EXISTS` on `JobParameter` next to the recurring-job filter. The value is a raw string, so it is compared as is (case-sensitive and without trailing spaces on SQL Server, as the Failed page's grouping does), not through the JSON forms `RecurringJobId` needs. The generic provider reads each scanned job's parameter raw, one storage call per scanned job: its scan stops at 1,000 matches, so for a rare exception it reads every scanned job's parameter until `SearchTimeoutSeconds`. The timeout is checked before each read, and a search stopped by it is reported as timed out. No connection is opened for it when the filter isn't set.
  - **The list offers what can match.** It shows the Failed page's exceptions with the same label parts on one line (short type, `Outer → Inner` for a wrapped exception, message, top frame and failed count), only those with a stored fingerprint, loaded when the panel opens under `SearchTimeoutSeconds`. Without any, it is disabled with a hint to register `UseDashboardFailureFingerprintFilter()`. On the generic provider, which can't tell stored from computed fingerprints, every labeled exception is offered.
  - **Linkable.** `search?exception=v1:…` selects the filter and runs the search, with a removable badge kept in sync with the panel as [#44](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/44) did for the other filters. A fingerprint in the address that isn't listed still shows as selected; a value that isn't a current fingerprint is ignored, so a malformed address can't become a query. A group on the Failed page links to it with **Search all jobs with this exception**, and says that Search may not find them when none of its failed jobs has a stored fingerprint (the Search panel leaves such groups out).
  - **API.** `JobFilterCriteria.FailureFingerprint` (applied through `EffectiveFailureFingerprint`, which drops non-current values) and `SearchRequest.ExceptionFingerprint`. A custom `IStorageQueryProvider` that doesn't know the new criterion ignores it.

### Known limitations

- **Search only finds failures that have a stored fingerprint ([#53](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/53)).** Failures recorded before `UseDashboardFailureFingerprintFilter()` was registered, or on a server without it, carry no `FailureFingerprint` parameter. The Failed page groups them by computing their fingerprint from the stored exception, but the Exception filter on Search can't find them.

### Documentation

- **README: which connection each dashboard read uses** ([#61](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/61)). The adapter's connection string serves only the adapter's queries (search, Analytics, heatmap Historical and estimated durations, the failed-job list on PostgreSQL). Realtime counters, the other job lists, job details, recurring jobs, servers, queues and most of the demand rollup go through Hangfire's `JobStorage` and the main pool shared with the workers. This wasn't apparent from the API, so a separate adapter connection string looked like it isolated all dashboard traffic.
- **README: Polling and Slow Storage** ([#64](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/64)). Describes the storage call limit, the back-off and every `PollingOptions` setting. The Health Checks section now explains how a slow or unreachable storage is reported (probe reuse, timeouts, skipped checks) and the asynchronous `HealthCheckService` methods.

## 2.5.7 — Responsive layout, wrapping job names, failure fingerprints

> **Patch release.** The dashboard now fits every screen from a 375px phone to a 2560px monitor: list tables hide their least important columns as they narrow and turn into cards on phones, and laptops get an icon-rail sidebar. Long job names wrap instead of being cut off ([#55](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/55)). ### Added

- **Failed jobs record a failure fingerprint ([#53](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/53)).** This is the first step toward grouping failed jobs by exception. The new opt-in server filter `FailureFingerprintFilter`, registered with `config.UseDashboardFailureFingerprintFilter()`, stores a `FailureFingerprint` job parameter such as `v1:5a633710a9709394` on every job that enters the Failed state. The value is the first 16 hex characters of a SHA-256 over three parts. The first is the exception type, plus the innermost exception's type when it wraps others. The second is the first line of the message (the innermost exception's) with run-specific values replaced by placeholders: GUIDs, dates and times, hex values, e-mail addresses, IPv6 and IPv4 addresses, URL query strings and numbers. The third is the top stack frame from the application's own code. Deadlocks with different process ids, or the same `NullReferenceException` rebuilt with its line moved, get one fingerprint. `Column 'Email' cannot be null` and `Column 'Phone' cannot be null` get two, even inside EF Core's `DbUpdateException`, and so do the same exception thrown from two different methods and the same driver error from two different jobs. No UI uses it yet; grouping on the Failed page follows.
  - **The top frame comes from the job's own namespace.** It is the first frame in the root namespace of the job's type (`MyApp` for `MyApp.Jobs.OrderJob`). Failing that, it is the first frame outside the framework and common libraries such as Npgsql, Dapper, Newtonsoft.Json, Polly, StackExchange.Redis, Azure and AWS (`FailureFingerprint.LibraryNamespaces`). It is kept without parameters, file or line number, and async, lambda and local-function names map to their containing method. The filter reads the job type from the state-change context only. A job whose type Hangfire could not load never ran, so its trace has no frame of its own and the type cannot change the value; reading it back from the storage would instead make the hash depend on whether the installed adapter fills in `JobData.InvocationData`.
  - **Wrapper exceptions are looked through.** `ExceptionDetails` starts with the exception chain (`Outer: message ---> Inner: message`). The innermost exception's type is added and its message used, while the outer type is kept. Generic arguments are dropped from type names, since they carry assembly versions that change with every deploy.
  - **Only final failures are fingerprinted.** The filter is an `IApplyStateFilter`, so it runs only when Failed is actually applied. Attempts that `AutomaticRetry` turns into retries never reach it, whatever the filter order.
  - **The fingerprint is computed from the stored strings, not the `Exception` object.** It uses the `ExceptionType`, `ExceptionMessage` and `ExceptionDetails` that `FailedState.SerializeData()` produces and Hangfire stores. A failure recorded before the filter was registered can therefore be fingerprinted later from its state data and stored job type, and gets the same value.
  - **The parameter is written through the state-change transaction when the storage supports it** (`JobStorageFeatures.Transaction.SetJobParameter`), and through the connection otherwise. It is stored as a raw string, not JSON, so SQL can compare it directly. It stays on the job when the job leaves the Failed state, and a later failure overwrites it. Any error in the filter is logged and the job fails as it would without the filter.
  - **The rules are public and versioned.** `FailureFingerprint.Compute` takes the stored exception strings and optionally the job's type name, and returns the fingerprint together with its parts (exception type, inner exception type, normalized message, top frame), and `FailureFingerprint.IsCurrentVersion` recognises values computed with the current rules. A rule change that alters fingerprints bumps the `v1:` prefix; a test pins an exact v1 value so such a change cannot slip through unnoticed.

The new shared `SortableHeader` component can be reused by other tables.

The **Queues** cards get a *Sort by* control (Name, Enqueued, Fetched) with a direction toggle, shown when there is more than one queue. The default stays by name. The same rules apply everywhere: rows without a value go last, and ties break by name or id.
  - **Sortable headers on the remaining full-list tables:** Throttling (Semaphores by Id, Usage or Holders; Held Mutexes by Id, Held By, State or Server; Rate-Limit Windows by Type, Id, Limit, Interval or Current Count), the semaphore details Holders table (Job, State, Server), Analytics → Recurring Health (Job ID, Status, Last Run, Avg Duration; Status descending lists Error and Warning first), Analytics → Queues (the queue status and server utilization tables, every numeric column), the Schedule Heatmap's recurring job table (Id, Queue, Time Zone, Est. ### Changed

- **Search does less work on large job tables ([#45](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/45)).** Every search used to run the substring match over the whole `Job` table twice: once for the total and once for the page, which was sorted by `CreatedAt` (no index).
  - **Pages come newest first by primary key** on SQL Server and PostgreSQL (`ORDER BY Id DESC`, the same order in practice since ids increase with creation time), so the database can stop once the page is full instead of sorting every match.
  - **The total is counted up to 1,000 matches** (`JobFilterCriteria.CountLimit`). Beyond that, Search shows **1,000+** (`PagedResult.TotalCountIsLowerBound` / `SearchResult.TotalCountIsLowerBound`), and the pager stops there with a hint to narrow the search. The generic provider already stopped scanning at 1,000 candidates; it now reports that as a lower bound instead of an exact total.
  - **PostgreSQL argument search can use a trigram index.** The argument predicate is now `arguments::text ILIKE …` without a `COALESCE`, which never changed the result (a null never matches) but kept an index from being used. The README has a new *Search on Large Instances* section with opt-in `pg_trgm` index definitions.
  - A search for a rare value still reads the whole table unless such an index exists; adding a state or date filter narrows it.

### Fixed

- **Clearing the `args:` or content badge on Search now clears the filter panel too ([#44](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/44)).** The × on those badges cleared the value from the search request, but the filter panel only copied the Arguments and Content fields from the page once, on first load. The old text stayed in the input, and the next change to any other filter sent it back, so the badge reappeared. The panel now remembers what it last sent and adopts the page's value whenever that differs, which is exactly an outside change such as a cleared badge. Text still being typed isn't rewritten by the normalized value sent up (trimmed arguments text, or content text under 3 characters sent as none). Clearing the content badge clears the text and leaves the Stack Trace / Console Output scope as chosen.
- **Search is no longer cut off after 5 seconds ([#43](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/43)).** The Search page cancelled every search after a hardcoded 5 seconds, which made search unusable on large instances and overrode any longer `Command Timeout` set in the storage connection string. The limit is now `DashboardUIOptions.SearchTimeoutSeconds`, defaulting to 30 seconds (the SQL Server and PostgreSQL default command timeout). Set it to `0` or less to remove the dashboard-side limit and let the storage's command timeout decide. The timed-out message shows the configured limit.
  - **A running search can be cancelled.** The Searching indicator now has a **Cancel** button. Starting a new search, changing page, or leaving the page also cancels the search still in flight, so an abandoned search no longer keeps a database query running.
  - **Cancelled SQL Server searches report as timed out.** SqlClient reports a cancelled command as a `SqlException` rather than an `OperationCanceledException`, so `SearchService` showed a timed-out SQL Server search as "storage error" and logged it as an error. An exception raised after the search's cancellation token fired is now reported as a timeout.
- **The Job Details snippet no longer misrepresents the invocation.** It hardcoded an activation line — `var sampleJobs = Activate<T>();` — for every job: the variable was always named `sampleJobs` regardless of the type, and the line was emitted even for `static` methods, which are never activated. Generic and nested types were printed as a bare `Type.Name` (losing type arguments and the outer type), and `async` methods were missing the `await` they would be called with. The renderer now derives the variable name from the type, omits activation for static methods, spells out generic and nested type names, and prefixes task-returning methods with `await` — the same output the original dashboard produces.
- **Argument values are no longer styled by guesswork.** The snippet formatted the live `Job.Args` objects rather than the stored payload, with a three-branch rule: `null`, `string`, and *everything else as a number*. Dates, booleans, enums, `TimeSpan`, collections, and complex objects were all rendered as bare `ToString()` output in number styling, and a `CancellationToken` printed its internal representation. Each type is now rendered as it would be written in C#.

### Known limitations

- Argument search matches the *stored* form, which is the serialized payload rather than the rendered call: a string argument keeps its JSON quotes and a `DateTime` is in round-trip format, so `args:2026-04-01T` finds a date argument while a locale-formatted date does not. The punctuation *between* arguments is not portable either — PostgreSQL stores the payload as `jsonb` and normalizes its spacing — so match on values, not on the separators.
- The generic (no storage adapter) provider still skips jobs whose `Job` failed to deserialize, so on that provider argument search — like name search before it — does not reach jobs the host cannot resolve. The SQL Server and PostgreSQL providers match those jobs, and the *display* of arguments works for them everywhere.

- **The Recurring Jobs "Items per page" selector did not paginate ([#37](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/37)).** `HandlePageSizeChanged` updated `_pageSize`, but the table iterated the complete `FilteredJobs` collection with no `Skip`/`Take`, and the shared `Pager` component was never placed on this page — so changing the page size only changed the selector's own value while every recurring job stayed rendered. The Stopped Jobs table had the same defect and received the same treatment with its own independent offset. Offsets reset on filter change and page-size change.

Both are now scoped to the current page.
  - **A shrinking list can no longer strand the pager on an empty page.** Nothing re-clamped the offset when the visible count dropped — after a delete, trigger, stop/start, or the page's own 10-second auto-refresh finding fewer jobs, the offset could point past the end, rendering an empty table under a stale "Showing X–Y of Z". Both offsets are now clamped back into range on every reload. This state was not reachable before, because the tables were unpaginated.
- **The recurring job editor dropped collection-typed arguments ([#39](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/39)).** An argument such as `Dictionary<string, string>` survived only as long as the JSON view was never left: opening Form view rendered it empty, and saving from there persisted `null`. `ParameterInputMapper.Map` classified it as `NestedObject`, because a dictionary *is* a concrete, publicly visible, non-abstract class and so satisfied `IsNestedObjectCandidate`. The nested sub-form builds its fields by reflecting over public writable properties — but a dictionary's entries are not properties, they live behind the indexer — so `BuildChildren` produced no fields to hold the data, `ApplyElement` found nothing to populate, and `SlotJson` serialized the empty result back as `null`. Collection types that implement `IEnumerable` without being arrays (`Dictionary<K,V>`, `List<T>`, `HashSet<T>`, and friends) now map to `ParameterInputKind.Json`, which already round-trips correctly through `JsonSerializer.Deserialize`. The check is placed after the existing array branch — which always returns — and after the `string` branch, so `T[]`, `byte[]`, and `string` are routed exactly as before.
- **A blank required parameter blocked the JSON ▸ Form toggle.** Found while verifying [#39](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/39) against the reported signature, and independent of collection types: switching the parameter editor back to Form was rejected outright with `Parameter 'x' is required.` whenever *any* required parameter was still empty, on any method that has one. `ValidateJsonForMethod` conflated two separate questions — whether the JSON is structurally usable, and whether the form is complete — behind a single gate, and the view toggle used that gate. Leaving a required field for later while shaping the rest of the job is ordinary mid-edit state, not an error, and toggling a view is not submitting. The method now takes a `requireAllPresent` flag: the JSON ▸ Form switch passes `false`, so only structural problems (malformed JSON, non-array, wrong element count, type mismatch) block it, and a blank required field repopulates into the form carrying its normal per-field required indication. `EmitJsonState` keeps `true`, so the `ParameterState` reported to `JobBuilder` still marks blank required parameters invalid and **submission remains gated on required-ness**.

### Changed

- **Test coverage for the parameter type mapping.** `ParameterInputMapperProperties` had a table-driven case for every row of the mapping table except collections; it now covers `Dictionary<string,string>`, `Dictionary<string,int>`, `List<string>`, `HashSet<int>`, and `IEnumerable<string>`, so the [#39](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/39) routing cannot silently regress. `InvalidJsonBlocksFormProperties` drops `required-missing` from its invalid-switch candidates — that is no longer a switch-blocking constraint — and gains a regression test asserting the switch succeeds while overall validity stays `false`.

### Added

- **Throttling pages ([#30](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/30), [#31](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/pull/31), contributed by [@d-lundy](https://github.com/d-lundy)).** Teams using the [Hangfire.Throttling](https://docs.hangfire.io/en/latest/background-processing/throttling.html) package had no visibility into their concurrency primitives from this dashboard — and because this dashboard replaces the built-in one, the Throttling package's own dashboard pages are not reachable either.   - **Orphaned-holder detection.** Three cases are flagged, each with its own explanation: the job record has expired out of storage, the job reached a final state without releasing its slot, or it is recorded as `Processing` on a server whose heartbeat has gone stale. Final states get a one-minute grace period first, since the release and the state transition are separate storage writes. Enqueued and Scheduled holders are deliberately not flagged.
  - **Reads the storage format directly**, with no dependency on the Hangfire.Throttling assembly — the same approach already used for `Hangfire.Console` and `Hangfire.Tags`. The layout was established by runtime observation of Hangfire.Throttling 1.4.3 against SQL Server, Redis, and in-memory storage, which produce identical keys despite very different physical representations.
  - **Nav item auto-detects.** The Throttling entry appears only when throttling data exists in storage, so hosts that do not use the package see no change. Detection is cached process-wide (`ThrottlingDetectionCache`), because the *negative* answer is the expensive one and would otherwise be recomputed on every circuit. Both pages refresh on a 6-second tick through a shared snapshot cache, so the cost is one storage pass per TTL across all open tabs rather than one per tab per tick.
  - Direct navigation without throttling data renders an explainer card with a configuration snippet, following the `AnalyticsNotAvailable` pattern.

### Fixed

- **Heatmap dropped cells and lost an hour across DST transitions.** `HeatmapTime.BuildWindow` computed its end as `start.AddDays(7)`, which on a `DateTimeOffset` adds 168 hours of *absolute* time while keeping the start's UTC offset. In a week containing a DST transition the end therefore drifted off local midnight: in a spring-forward week the window ran an hour past it, so an in-window fire could bucket at day index 7 — and since `PlannerHelpers` builds cells for days 0–6 only, those fires were dropped from the grid with no indication; in a fall-back week the window ended an hour early, so the last local hour of day 6 was never projected at all. The end is now local midnight seven calendar days after the start, matching the seven local days the grid indexes, so the absolute duration is 167, 168, or 169 hours. This also resolved a contradiction inside the test suite, where one property asserted a fixed 168-hour duration while another asserted an in-window day index of 0–6 — assertions that cannot both hold in a spring-forward week. The failing property was seed-driven, which is why it surfaced only intermittently.
- **Unguarded use of Hangfire's optional storage API could fail the whole dashboard shell.** `GetSetCount`, `GetRangeFromSet`, and `GetValueFromHash` are `virtual` on `JobStorageConnection`, not `abstract`, and throw `NotSupportedException` for the `Storage.ExtendedApi` feature unless a storage overrides them. Hangfire.SqlServer and Hangfire.PostgreSql do; a storage is not required to. `TagsDataReader.GetTagsCount()` is called from `NavMenu`, which is part of the layout, so on such a storage this did not hide a nav counter — it failed the circuit and took down the shell on every page. A new `a2n.Hangfire.Dashboard.Storage.SetCounting` helper falls back to `GetAllItemsFromSet` (which is `abstract`, so always implemented), and is applied in `TagsDataReader`, `AuditLogService`, `HangfireMonitorService`, and `ConsoleDataReader`. Console progress now degrades to no value rather than throwing; console *lines* cannot fall back, since their order comes from the set score and `GetAllItemsFromSet` is unordered, so unsupported storages report no console data instead of a scrambled log. `AuditLogService` was not throwing — its call sites already sat inside broad catches — but those returned `0`, rendering an empty Audit page with a wrong pager; its counts now work.

### Changed

- **The PostgreSQL test suite now skips instead of failing when no server is reachable**, matching what the SQL Server suite already did. `PostgreSqlFixture` opened its connection in `InitializeAsync` with no guard, so all 142 tests failed with `NpgsqlException` on a machine or runner without PostgreSQL — which is also what made the first CI run red. The fixture now records availability, exposes `RequireAvailable()`, and every test guards itself via `SkippableFact` / `SkippableTheory`. It also reads `ConnectionStrings__PostgreSql` from the environment, so CI and contributors can point the suite at their own server without editing a committed file.
- **Continuous integration.** The repository previously had no CI: `publish.yml` runs only on `release: published`, so nothing validated a branch or a pull request. A new `Build & Test` workflow builds the solution and runs its six test projects across net8.0, net9.0, and net10.0 on every pull request (to any branch, so PRs targeting integration branches are covered), on pushes to `main`, and on demand. PostgreSQL runs against a service container; the SQL Server suite skips itself when no server is reachable.
- **bUnit render-wait timeouts raised to 30 seconds** across 16 call sites via a shared `TestTimeouts.RenderWait`. `StatCards_AlwaysRenderExpectedLabels` failed intermittently when the suite ran all three target frameworks concurrently, while passing in 545 ms on its own against a 5-second budget. A render-wait timeout only exists so a stuck render fails instead of hanging, so a generous value costs nothing on the passing path — and intermittent red teaches everyone to ignore red.

### Deferred

- **Detach (the throttling recovery action) is not included.** [#31](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/pull/31) originally shipped a Detach button for orphaned semaphore holders and held mutexes, with audit-log entries. The read path is backed by runtime observation of the storage format, but the keys Detach *writes* to — the semaphore holder set, the mutex registry pair, and the mutex holder set — have no such evidence yet: the verification probe registers a semaphore but never drives a job through it, and never acquires a mutex. Since a wrong read shows an empty column while a wrong write corrupts a concurrency invariant, Detach is held until a probe run with `[Semaphore]`- and `[Mutex]`-attributed jobs confirms the holder-set layout and whether occupancy is tracked anywhere other than the holder set's cardinality. The monitoring pages are fully functional without it.

## 2.5.2 — Rollup completeness

> **Patch release.** Closes the sampling gap v2.5.1 left open on non-SQL storages ([#29](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/29)): under bursty load the rollup collector recorded only what one poll could reach and advanced past the rest. Confined to `a2n.Hangfire.Dashboard.Rollup`; no public API change and no migration.

### Fixed

- **The rollup collector dropped executions beyond its per-poll cap ([#29](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/29)).** `ExecutionRollupCollector` kept a single watermark per state and scanned the monitoring API newest-first, stopping at 2 000 jobs per poll. When more than that completed inside one 60-second poll, the pass recorded the newest 2 000 and then advanced the watermark to the newest tick it had seen, so everything older but still newer than the previous watermark fell below the new watermark and was never aggregated — an unbounded shortfall that made the rollup a sample rather than an aggregate. The collector now tracks the *range* it has covered (`succeededCoveredFloorTicks` / `succeededCoveredCeilingTicks`, and the failed-state equivalents) instead of a single boundary: a capped pass leaves the watermark where it is, records the range it reached, and the following polls step over that range for free — no job-parameter lookups — and drain the remainder downward until they meet the watermark, at which point both boundaries collapse back into one. A burst larger than one poll's cap is therefore aggregated in full across subsequent polls, and because the rollup counters are additive, the covered range is what keeps executions from being counted twice. The per-poll budget is also soft at the tail: a pass finishes the tick it stopped on, so storages that truncate timestamps cannot have same-tick executions split across the boundary and lost or replayed.
- **The per-poll warning now fires only when data is genuinely unrecoverable.** Hitting the cap is normal and recoverable, so it is reported at information level along with how much history is still pending. The warning is reserved for the one case that remains lossy: so many jobs completed while an earlier backlog was still draining that the pass could not reach the previously covered range, leaving two disjoint ranges that cannot both be represented. They are merged rather than re-scanned, since re-scanning would double-count.

### Changed

- Rollup state written by earlier versions reads back as "no gap open", so upgrading needs no migration and no reseed.

## 2.5.1 — Redis / rollup analytics fixes

> **Patch release.** Fixes the Analytics regressions reported on Hangfire Pro with Redis storage ([#25](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/25), [#26](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/26), [#27](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/27)), and carries the nav-group circuit crash fix ([#23](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/23)) previously shipped as `2.5.1-beta.1`. The analytics work is confined to the rollup adapter used by non-SQL storages, plus one additive interface method and the Recurring Health page.

### Fixed

- **Heatmap estimated duration always showed `1m` ([#27](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/27)), and the Duration panels were empty ([#26](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/26)).** `MetricsRollupStore.ReadJobDurationStats` recovered job-type names by selecting hash fields that contain no `:`, but every field is written as `{jobType}:count`, `{jobType}:sum`, … so the filter matched nothing and the method always returned an empty list. `EstimatedDurationResolver` therefore never received a p95 and fell back to the floored 1-minute default, while Analytics ▸ Performance lost *Duration trend* and *Duration by job type*. Prefixes are now recovered from the trailing `:count` marker, which also keeps job types and queue names that contain `:` intact.
- **Queue latency had no data ([#26](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/26)).** `ExecutionRollupCollector` always passed `latency: null`, so the per-queue latency rollup stayed empty. It now reads `Latency` from the succeeded state's own data.
- **Job durations were over-reported on non-SQL storages.** The collector used `SucceededJobDto.TotalDuration`, which is the enqueued wait *plus* execution time. It now prefers `PerformanceDuration` from the state data — matching what the SQL Server / PostgreSQL adapters read — and only falls back to `TotalDuration` when the state data is unavailable.
- **Average state timing had no data ([#26](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/26)).** `RollupMetricsProvider.GetAverageStateTimingsAsync` returned an empty DTO. It now derives the enqueued and processing phases as count-weighted means of the latency and duration rollups.
- **Queue throughput dropped data points for queues whose name contains `:`.** `ReadQueueThroughput` split the `{queue}:{bucket}` field on the first colon, so such queues produced an unparseable bucket key and were silently discarded. It now splits on the last colon; the bucket key is a `yyyy-MM-dd-HH` stamp and never contains one. Same class of defect as the duration-stats bug above, found while auditing the other readers.
- **Analytics ▸ Recurring never finished loading on large deployments ([#25](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/25)).** `GetRecurringJobExecutionsAsync` paged the succeeded and failed lists (up to 2 000 jobs each) and probed the `RecurringJobId` parameter of every job it saw — a separate storage round-trip per job. The health page calls it once per recurring job, so the cost was O(recurring jobs × 4 000) round-trips. The collector now maintains a bounded ring of the 20 most recent executions per recurring job, and the provider answers from a single hash read.
- **Recurring Health fetched execution history one job at a time ([#25](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/25)).** The page looped over every recurring job, so even a cheap per-job lookup cost one storage round-trip each. A new `IStorageMetricsProvider.GetRecurringJobExecutionsBatchAsync` fetches history for all jobs at once — one `ROW_NUMBER` query on SQL Server / PostgreSQL, one hash read on the rollup adapter. It is a default interface method that falls back to the per-job loop, so third-party providers keep working unchanged. The page also cancels its in-flight queries when the user navigates away.
- **Recurring health showed no "Last 5 Results" and no average duration ([#25](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/25)).** `GetRecurringJobHealthAsync` hard-coded `LastExecutionResults` to an empty array and never set `AverageDurationMs`. Both are now filled from the new recurring-execution rollup in one hash read for all jobs.
- **Sidebar nav group tore down the Blazor circuit on a fresh session ([#23](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/23)).** First shipped in `2.5.1-beta.1`. When no `hf-nav-group:*` key existed in `localStorage`, `NavMenuGroup` read the persisted expand state via `JS.InvokeAsync<bool?>`. On some `Microsoft.JSInterop` versions, deserializing a JavaScript `null` into `Nullable<bool>` routes through `Convert.ChangeType(null, typeof(bool))` and throws `InvalidCastException`; the surrounding `try/catch` only handled `JSDisconnectedException` / `ObjectDisposedException`, so the resulting `JSException` propagated out of `OnAfterRenderAsync` and terminated the circuit — making sub-pages unreachable. `Content/js/nav.js` now returns a string (`"true"` / `"false"` / `""`) instead of `null`, the component reads it with `JS.InvokeAsync<string>` + `bool.TryParse` (avoiding the value-type conversion path entirely), and a defensive `catch (JSException)` preserves the default expanded state on any runtime.

### Changed

- **The rollup collector now warns when it is sampling rather than aggregating everything.** Each poll scans at most 2 000 succeeded and 2 000 failed jobs; beyond that the watermark advances past the unscanned executions and they never reach the rollup. The collector logs a warning when it hits that cap so the shortfall is visible in the logs instead of showing up as quietly understated metrics. Closing the gap entirely needs a resumable two-watermark scan, tracked in [#29](https://github.com/anwarminarso/a2n.Hangfire.Dashboard/issues/29).

### Known limitations

- Rollup data remains forward-only: panels populate from the first collector run after upgrading (the collector polls every 60 seconds), and the recurring history ring holds the last 20 executions per job. `AvgScheduledMs` stays `0` because the pre-enqueue phase is not tracked by the rollup.
- Under sustained load above ~2 000 completions per minute the rollup is a sample, not a complete aggregate (see the warning above). Use the SQL Server or PostgreSQL adapter when complete history is required.

- **🧩 Guided parameter form** — a type-aware form generated from the method signature (text, numbers, dates, GUIDs, enums, booleans, arrays, nested objects) with a live JSON mirror and a Form ⇄ JSON toggle.
- **🔎 Method discovery** — pick from methods discovered across loaded assemblies, with overload-safe resolution. Hand-typed arbitrary methods are opt-in via `AllowArbitraryMethodInvocation`.
- **🕑 Visual cron builder** — build a schedule field-by-field (every / specific / range / step) with a human-readable description and a next-run preview in the selected time zone.
- **➕ Enqueue page** — the same builder powers a new `/jobs/enqueue` page for one-off (fire-and-forget) jobs.

### Added — Job Builder

- **Typed argument conversion** — operator-supplied values are converted to each parameter's declared CLR type before the job is stored (`["some-value", 42]` → `string`, `int`), matching how Hangfire serializes arguments. Empty fields resolve to `null` for nullable types or `default(T)` for non-nullable types — never an error.
- **Overload-safe method resolution** — `JobMethodResolver` selects the single overload whose job-parameter count and types match the supplied arguments. Ambiguous, missing, or non-matching methods are rejected with an identifying error and never touch storage.
- **Method discovery** — `JobMethodResolver` scans loaded assemblies for public methods whose method or declaring class carries `JobDisplayName`, `Tag`, or `Queue`. The result is cached for the dashboard's lifetime and resilient to assemblies that fail to load (`ReflectionTypeLoadException`).
- **`Parameter_JSON` validation** — well-formedness, "must be an array", argument-count-vs-signature, and per-element convertibility are validated, with errors naming the offending parameter and expected type.
- **Injected parameters skipped** — `PerformContext`, `IJobCancellationToken`, and `CancellationToken` are excluded from the form and filled by Hangfire at runtime.
- **Edit pre-fill** — current argument values are loaded back into the form when editing an existing recurring job.
- **Visual cron builder** — `ScheduleBuilder` offers a field-by-field cron editor plus manual input, with a human-readable description and next-occurrence preview (parsing via Cronos, already bundled with Hangfire — no new dependency). Unparseable expressions are flagged and block submission.
- **Queue handling** — the queue control suggests current queues (defaulting to `default`) and is an editable combobox that also validates free text against Hangfire's queue-name rule (`^[a-z0-9_-]+$`, max 50 chars); when a `[Queue(...)]` attribute applies to the method or its declaring class, the control becomes read-only with a precedence notice, because Hangfire's `QueueAttribute` overrides the stored queue at state election.
- **Searchable time zone + inline validation** — the recurring editor's time zone is a searchable combobox, and the Job ID, queue, and time-zone fields validate inline. A new recurring Job ID is held to the same strict `^[a-z0-9_-]+$` rule (max 50 chars) because it is carried in the `/recurring/edit/{JobId}` route; existing ids are not re-validated on edit so legacy jobs keep working.
- **Enqueue page** at `/jobs/enqueue` — reuses the `JobBuilder` composite in Enqueue mode for one-off jobs; `HangfireMonitorService.EnqueueJob` returns the new job id. Reached via an **Enqueue Job** button on the Enqueued jobs page (the dedicated nav entry was removed).
- `DashboardUIOptions.AllowArbitraryMethodInvocation` (default `false`) — gates whether operators may invoke hand-typed type + method, keeping the arbitrary-invocation surface opt-in.

### Changed

- The recurring **Create/Edit** form is now built on the shared Job Builder, so it supports arguments, method discovery, and the visual cron builder. `HangfireMonitorService.CreateOrUpdateRecurringJob` now takes a `RecurringJobRequest` and persists arguments and the configured queue.
- **Option rename.** `EnableRecurringJobAdmin` → **`EnableJobManagement`**; its scope now also gates the Enqueue page. The old name is kept as an `[Obsolete]` alias for source compatibility and will be removed in a future release. `EnableCustomMethodInvocation` → **`AllowArbitraryMethodInvocation`** (hard rename — this option was introduced in this release).

### Gating

- Read-only mode, `EnableJobManagement`, and `AllowArbitraryMethodInvocation` are all enforced in both the UI (banners + disabled controls) and the service layer.
- When `EnableJobManagement` is `false` the recurring create/edit builder is hidden, the **Enqueue Job** button and nav entry are not shown, and the `/jobs/enqueue` route returns **Not Found**.

### Internal

- New `JobMethodResolver` service; `Internal` helpers `JobArgumentConverter`, `ParameterInputMapper`, `CronDescriber`, `CronPreview`, `EffectiveQueue`; shared models in `Models/JobBuilderModels.cs`; components `JobBuilder`, `MethodPicker`, `ParameterBuilder`, `ScheduleBuilder`.
- Test coverage: 25 FsCheck.Xunit correctness properties over the pure logic (argument converter, resolver, input mapper, Form/JSON round trip, cron helpers), plus bunit component tests and service tests.

## 2.3.1 — Realtime Analytics Fixes

> **Patch release.** Restores realtime analytics on SQL Server and keeps the analytics broadcast on a steady cadence under load. NuGet packages now ship API documentation.

### Fixed

- **Realtime analytics never broadcast on SQL Server.** `GetQueueDepthSnapshotAsync` and `GetQueueThroughputAsync` placed a subquery in the `GROUP BY` list, which SQL Server rejects (error 144). This threw on every `AnalyticsBroadcastService` tick, so the analytics SignalR channel stayed silent on SQL Server while it worked on PostgreSQL. The queue expression is now computed once in a derived table and aggregated in the outer query (mirrors the PostgreSQL provider). Verified `AnalyticsUpdate` broadcasts every 5s on SQL Server.
- **Analytics broadcast drifted off cadence under load.** The broadcast loop delayed the interval *after* finishing its work, so the real period was `query_time + interval` (p95 ~50s instead of the 5s target in a 300s SQL Server load test). The loop now uses a `PeriodicTimer` so ticks fire on a fixed schedule (ticks arriving mid-broadcast are coalesced instead of drifting), and runs the three independent metrics queries (throughput, server utilization, queue depth) concurrently via `Task.WhenAll` so per-broadcast cost is the slowest query rather than their sum. A `Warning` is now logged when a broadcast exceeds the cadence. Verified p95 5.1s on SQL Server in the 300s persona scenario.

### Build / Docs

- **NuGet packages now ship XML API documentation.** `GenerateDocumentationFile` is enabled for Release builds (`NoWarn 1591`), and the XML doc `cref`/`param` references this surfaced were corrected in `PgHelper`, `HangfireDashboardHealthCheckExtensions`, `AuditLogService`, and `JobParameterMatching`.

### Internal

- Added a SQL Server metrics-provider integration test project (`a2n.Hangfire.Dashboard.SqlServer.Tests`) mirroring the PostgreSQL one — a per-run unique schema fixture, a deterministic 100-job seeder, and smoke tests exercising all 15 `IStorageMetricsProvider` queries against a real SQL Server (regression coverage for the error 144 fix). Tests skip rather than fail when no SQL Server is reachable, so CI without a database stays green.
- Added a Python load-testing harness under `tests/load/` (stress, scenario, and end-to-end utilities) used to validate the analytics cadence fixes. Secrets (`config.toml`) and generated artifacts stay untracked.

## 2.3.0 — Operational Visibility & Controls

> **The biggest operations-focused release yet.** v2.3.0 turns the dashboard from a *viewer* into an *operational tool*: health probes for your orchestrator, an at-a-glance health hero card, live queue pause / maintenance mode, and a full audit trail of admin actions.

### ✨ Highlights

- **🩺 Health checks** — `/healthz`, `/healthz/ready`, `/healthz/full` endpoints + an ASP.NET Core `IHealthCheck` adapter, plus a traffic-light **health hero card** on the Home page.
- **⏸️ Queue pause / resume** — pause individual queues from the new `/queues` page; workers reschedule jobs instead of running them (no data loss).
- **🚧 Maintenance mode** — one global toggle pauses every queue, with a persistent banner on every page.
- **📋 Audit log** — every admin action recorded (who, when, what) on a new `/audit` page, attributed to the real signed-in user.

### Added — Health checks

- **Health check endpoint** at `/{dashboard}/healthz`, `/healthz/ready`, and `/healthz/full`. Returns a structured JSON `HealthReport` covering storage availability, server liveness, queue depth, stuck processing jobs, last-hour failure rate, and missed recurring schedules. HTTP 200 for `Healthy`/`Degraded`, HTTP 503 for `Unhealthy` (K8s probe convention).
- **Health hero card** on the Home page — at-a-glance traffic light (Healthy / Degraded / Critical) with per-issue descriptions, deep-link actions, and an auto-refresh every 10 seconds. The detailed 8-card stat grid is now collapsible behind a "Detailed metrics" toggle (its expanded/collapsed state is remembered per browser).
- `DashboardUIOptions.HealthCheckAuthorizationMode` (`AllowAnonymous` default for K8s, `LocalOnly`, or `RequireDashboardAuth`).
- `DashboardUIOptions.HealthCheckThresholds` to tune what counts as Degraded vs Unhealthy (queue depth, failure rate, stuck-processing minutes, server heartbeat tolerance, recurring missed tolerance, storage response time).
- `HealthCheckService` (DI-registered) — also usable from host code if you want to wire the report into your own ASP.NET Core HealthCheck pipeline.
- `HealthReportCache` — process-wide single-flight cache so concurrent circuits and probes share one computed report; manual hero-card refresh bypasses it.
- `services.AddHealthChecks().AddHangfireDashboard()` adapter — register the dashboard as a single ASP.NET Core `IHealthCheck` for hosts that prefer a unified `/health` endpoint aggregating multiple dependencies. Per-check status surfaces via `HealthCheckResult.Data`.

### Added — Operations (queue pause, maintenance, audit)

- **Queue pause / resume** — toggle individual queues from the new `/queues` page (a modern card layout with status dots, live counts, and a summary bar). While paused, Hangfire workers reschedule jobs (default +30s) instead of executing them. Requires registering the server filter in the host app: `config.UseDashboardQueuePauseFilter()`. When the filter is missing, the page shows an actionable warning instead of silently doing nothing.
- **Maintenance mode** — global pause-all toggle from the Queues page header. A persistent yellow banner with a `Manage →` link is rendered on every dashboard page. Optional reason field surfaced in the banner.
- **Audit log** — every admin action (job requeue/delete, batch ops, recurring CRUD, recurring stop/start, queue pause/resume, maintenance toggles) is recorded with timestamp, user, client IP, target, and metadata. New page at `/audit` with filter by action prefix, user, and target. Storage uses Hangfire's KV primitives (`audit:log` set + `audit:entry:{id}` hashes) — no schema changes. Configurable retention (`Retention`, default 30 days) and max entries (`MaxEntries`, default 10,000).
- `DashboardUIOptions.AuditLog` (`Enabled`, `Retention`, `MaxEntries`).
- `DashboardUIOptions.QueueOperations` (`Enabled`, `Behavior` — Reschedule or Requeue, `RescheduleDelay`, `PauseStateCacheTtl`).
- `AuditLogService` and `QueueOperationsService` — DI-registered (scoped) services usable from host code. Action attribution uses a per-circuit `AuditActorAccessor` populated from `AuthenticationStateProvider`, so audit entries record the actual signed-in user even though Blazor circuit actions run without an `HttpContext`.
- `QueuePauseServerFilter` — Hangfire `IElectStateFilter` that intercepts the transition into `Processing` and reschedules/re-enqueues jobs on paused queues. It never cancels execution, so paused jobs are never moved to `DeletedState` (no data loss). Pause/maintenance state is read through a per-server cache (default 2s TTL).
- `QueueOperationsStateCache` — process-wide short-TTL cache shared by the nav menu, maintenance banner, and Queues page so pause/maintenance state is read once per interval instead of per circuit.
- New nav entry **Audit Log** under Management; new nav entry **Queues** with paused-count badge.

### Added — Other

- `IDashboardAsyncAuthorizationFilter` and Hangfire filter adapters.
- `DashboardUIOptions.LoginPath` for redirecting unauthenticated users to a login page.
- `samples/SampleAppAuth` — cookie authentication demo with login form.
- `MetricsQueryCache` with per-key stampede protection for analytics queries.

### Added — Enhanced Job Details

- **Continuation dependency graph** on the Job Details page — visualizes `BackgroundJob.ContinueJobWith(...)` chains. Walks up to the root parent then expands descendants, with edge labels for the continuation condition (`on succeeded` / `on deleted` / `on any`). Clickable nodes, dashed placeholders for expired/deleted jobs, and a **Load more** button bounded by `JobGraphMaxDepth` (default 5) and `JobGraphMaxNodes` (default 30).
- **Retry summary banner** above the state history — shows the retry count and whether every attempt failed with the same exception type (a quick signal for a persistent root cause vs flaky failures). Each Processing/Failed state is numbered with its attempt index.
- **Stack trace source links** — file references in exception stack traces (`... in {path}:line {N}`) become clickable links to your source provider. Built-in presets for GitHub, GitLab (incl. self-hosted), Azure DevOps, Bitbucket, and local IDEs (`vscode://`, etc.), plus a custom `UrlPattern`. Configure via `DashboardUIOptions.SourceLink`; path normalization helpers `WithPathStrip(...)` / `WithPathReplace(...)`. Only safe URL schemes are rendered as links.

### Security

- **BREAKING:** `DashboardUIOptions.Authorization` now defaults to `LocalRequestsOnlyAuthorizationFilter` (same as Hangfire built-in dashboard). Remote hosts receive HTTP 401 unless you set `Authorization = []` or add your own filters.
- SignalR hub and Blazor circuit paths now require the same authorization as dashboard pages.
- Schema/table identifiers from configuration are validated (`^[a-zA-Z_][a-zA-Z0-9_]*$`) before use in SQL.

### Fixed

- Audit log appeared empty on SQL Server / PostgreSQL: `GetRangeFromSet` was called with `int.MaxValue`, which those providers compute as `endingAt + 1` (overflowing to a negative bound and returning zero rows). Now uses a safe upper bound.
- Queues page now lists configured/paused queues even when they hold no jobs (Hangfire's `Queues()` only returns non-empty queues), showing real `0` counts instead of a dash — so a paused, idle queue is still visible and resumable.
- `MetricsQueryCache` no longer removes per-key semaphores after release (fixes TOCTOU stampede race).
- SQL Server percentile queries use `PERCENTILE_CONT ... OVER (PARTITION BY ...)` (valid T-SQL).
- Antiforgery validation skipped for `/_blazor` and `/hubs/*` negotiate endpoints.
- PostgreSQL throughput timeline includes daily counter keys (`stats:*:yyyy-MM-dd`).
- Queue resolution prefers `Job.Queue` job parameter, then legacy dashboard `CurrentQueue` (not Hangfire core), then state JSON on Enqueued/Processing.
- Queue latency metrics read `Latency` from **Succeeded** state (Hangfire stores it there), with queue from `Job.Queue` parameter.
- Recurring job execution history matches `RecurringJobId` job parameters in both plain and JSON-serialized forms (Hangfire 1.8+).
- Public `JobParameterMatching` helper in `a2n.Hangfire.Dashboard.Storage` for storage adapter packages.

### Notes for deployments behind reverse proxy

`LocalRequestsOnlyAuthorizationFilter` checks `Connection.RemoteIpAddress`. Behind a reverse proxy without forwarded headers, the remote address may appear as loopback and **allow all clients**. Configure `UseForwardedHeaders()` and restrict access at the proxy when deploying to production.
